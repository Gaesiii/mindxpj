# qr - M05 / Member 2

B09-B11/B13 implement API-only dynamic QR and in-person verification. No camera frontend, recognition, scheduler, worker or infrastructure service is included. PM/member review and API_Gate remain pending.

Staff `POST /api/v1/sessions/:id/qr-challenges` with `{}` for an OPEN scoped session receives201: challenge id/session_id, opaque token, issued_at/expires_at, refresh_after_seconds30 and qr_image_base64 PNG. Token uses256 random bits and only SHA-256 hash is stored. Each challenge expires after60 seconds; older tokens remain usable until their own expiration. A client requests a fresh challenge every30 seconds; the API does not run background refresh. Tokens contain no student data and are excluded from logs/idempotency payloads.

Student `POST /api/v1/qr-scans` receives only `{token}` plus Idempotency-Key. Student identity always comes from the active linked session account. Current class and immutable roster must match, the session must be OPEN and challenge unexpired. Unknown token gives422 QR_INVALID, expired token422 QR_EXPIRED, missing/current-class-mismatched roster422 ROSTER_REQUIRED. Extra student_id/session_id/source fields are rejected422; staff cannot scan on behalf of a student. Scanning creates PENDING with server scanned_at, immutable first timestamp and15-minute verification expiry, leaving Attendance UNMARKED. Conditional unique ensures one pending scan per roster; repeated valid scans return the same pending record200. Multiple students may use the same challenge.

Student GET `me/today-sessions` returns current-class own OPEN/CLOSED roster sessions for Vietnam today; GET `me/scan-status?session_id=:id` returns own scan and attendance. Staff GET `sessions/:id/qr-scans?status=PENDING` returns scoped queue entries with identity snapshots and an authorized photo endpoint URL when available within current Student class scope; historical snapshots do not grant access to transferred-student photo metadata. Unsupported filters return422. Pending expiry is evaluated synchronously on scan/status/queue/roster/verification endpoints, without a background job.

Staff POST `qr-scans/:id/confirm` requires Idempotency-Key, expected_scan_version, expected_attendance_version and identity_confirmed JSON true. Optional uniform object accepts observed_uniform/uniform_status/reason/note. Confirmation uses scanned_at as arrived_at, source QR and current server verification timestamp; omitted uniform remains NOT_CHECKED. Attendance, uniform, scan, ChangeLog and stored retry response commit together. Any uniform/version error rolls them back. Challenge need not still be valid at verification, but the PENDING scan must still be within15 minutes and session OPEN. POST `qr-scans/:id/reject` receives expected_scan_version/reason plus key; rejection records no presence.

Successful same-key retries recheck role/current class scope first, then replay original status/body even after close. Canonical scan hashes contain a token fingerprint only. A confirmed scan returns its CONFIRMED state200 when a later valid scan arrives; manual/ABSENT attendance returns `{scan,attendance}`200 and is preserved. REJECTED/EXPIRED can scan anew while OPEN and unrecorded. Manual recording supersedes pending scans; close expires them. Invalid verification state returns409; wrong version409 VERSION_CONFLICT.

Scan rate limit:30 attempts per authenticated student per60-second window, using Django LocMemCache. Invalid token/schema/roster attempts consume quota. Successful idempotency retries replay without consuming quota.429 includes Retry-After. This is a per-process local-demo limit; it is neither distributed nor durable across restarts. No Redis/queue/cloud dependency is added.

Verification: tests.test_qr has11 API cases for shared tokens, session identity, expiry, repeat timestamps, independent expiry persistence, scope/retry after close/transfer, manual supersession, reject and uniform rollback; tests.test_full_flow has2 real workflow/CSRF cases. Run `.venv/Scripts/python.exe manage.py test tests.test_qr tests.test_full_flow` in backend with process DJANGO_SECRET_KEY. Review/PM evidence is separate from executable tests.
